────────────────────────────────────────────
SUPPORTED POLICY OPERATORS
────────────────────────────────────────────
<=          Numeric: value must be <= threshold
>=          Numeric: value must be >= threshold
<           Numeric: value must be < threshold
>           Numeric: value must be > threshold
==          String equality (case-insensitive)
!=          String inequality (prohibited value check)
exists      Term must be present with a non-empty value
in          Term value must appear in comma-separated allowed list
not_in      Term value must NOT appear in comma-separated prohibited list
semantic    Always → NEEDS_HUMAN_REVIEW (requires LLM / human judgment)
(unknown)   Always → NEEDS_HUMAN_REVIEW with explanation

Numeric parsing handles: bare floats, N%, Nx (ratios), INR N,NNN,NNN, "N months", etc.

────────────────────────────────────────────
KNOWN LIMITATIONS
────────────────────────────────────────────
1. Term matching is by name equality (rule.name == term.name, case-insensitive).
   Rules must be authored with the exact same name as the extracted term.
   A term_name field on PolicyRule would remove this coupling (future enhancement).

2. Numeric parsing handles the most common formats. Edge cases (e.g., "INR 8 crore",
   "five percent") are not parsed and return NEEDS_HUMAN_REVIEW. The normalized_value
   field from the extraction agent mitigates this in practice.

3. 'semantic' operator always returns NEEDS_HUMAN_REVIEW. No LLM semantic
   evaluation is implemented in Module 4 (by design).

4. Multi-term rules (same name, multiple terms) use worst-status selection.
   If two terms for the same name produce PASS and FAIL respectively, the
   result is FAIL (conservative). This is intentional safety behavior.

5. The Risk/Summary Agent (Module 5) is not yet implemented.
